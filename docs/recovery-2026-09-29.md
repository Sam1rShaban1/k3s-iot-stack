# Cluster Recovery — 2026-09-28/29

P0.6. The cluster had been down for roughly four months. This records what was
actually wrong, because the failure modes are the point: **not one of them was
visible in the Git repository.** Every one lived in node state that no
ArgoCD Application reconciles.

This is directly relevant to the follow-on work. Detector class 9 in the plan
covers "config drift visible in Git"; this incident is the complementary case —
**host-level drift that Git cannot see at all.**

## Host-level packages the cluster silently lost

Two packages were absent from worker nodes, and both are fatal in ways that look
like Kubernetes bugs rather than package problems:

- **`open-iscsi`** — Longhorn refuses to start without `iscsiadm`. The pod
  exits 1 with a message that only appears in `kubectl logs`, not in the pod
  status, so a status-based detector misses it.
- **`iptables`** — k3s embeds kube-proxy, which programs ClusterIP DNAT through
  iptables. With the package gone, kube-proxy starts cleanly, reports no
  error, and programs **zero** rules. The symptom is `connection refused` on
  every ClusterIP from pods on that node, while the host itself can still reach
  the ClusterIP. This looks exactly like the ClusterIP resolution failure the
  paper attributes to k3s version skew (§V-E1d) — and version skew was *not* the
  cause here.

**Neither is declared in the repository.** `pi-setup.yml` installs base
packages but never asserts that the packages Longhorn and kube-proxy require
are present. That assertion belongs there; it is a prerequisite for any agent
that must reason about node health, because "is this host provisioned
correctly?" is currently unanswerable from Git.

## Air-gapped operation

The cluster has no route to the internet:

```
dial tcp deb.debian.org:443: connect: no route to host
dial tcp quay.io:443:      connect: no route to host
```

Consequences:

- `apt-get install` does not work on any node. Packages were fetched on a
  separate machine and side-loaded with `dpkg -i`.
- Images not already cached on a node cannot be pulled. ArgoCD and Longhorn
  instance-managers are affected.
- Harbor (192.168.1.50:30500) is running but holds **no repositories**, so it
  is not usable as an internal mirror as currently configured.

`longhornio/longhorn-instance-manager:v1.7.2` could not be resolved: it is
absent from every node, and a local pull returned the **amd64** variant because
the fetching machine is x86_64 while the nodes are arm64. This is unresolved.
It is not yet blocking: the only Longhorn volume the benchmark path needs is
VictoriaMetrics', and that volume is `attached` / `healthy` / writable.

## Bugs found in my own P0 work

The recovery surfaced three defects introduced earlier the same day, all caught
by the harness rather than by inspection:

1. `preflight.check_cluster_reachable` was changed to return `bool` but never
   returned `True`, so `run_preflight` short-circuited and the whole preflight
   reduced to three checks while still exiting 0 — a silent false pass. Only
   visible because the preflight was run against a live cluster.
2. `network-policies.yaml` selected benthos and emqx pods with
   `app.kubernetes.io/name`, but those manifests declare `app`. The policy
   would have matched no pods — the same class of bug the file was corrected
   for. Preflight reported three components as "no pods match", which is what
   exposed it.
3. The harness resolved the broker to the master's `InternalIP` (10.0.0.1),
   which is unroutable from the machine running the harness. Discovery now
   probes candidates for TCP reachability and returns the first that answers.

## Reproducible artefacts

- `ansible/k3s-setup.yml` — repaired: publishes the join token to the worker
  group instead of reading a file written on the master, pins
  `INSTALL_K3S_VERSION`, stops stray units before installing, and supports
  `k3s_rejoin` for the CA-mismatch case in fault 1.
- `ansible/inventory.ini` — corrected addresses. pi2 and pi7 had moved off
  10.0.0.0/24 onto the LAN via DHCP, and pi3/pi4 were never in the inventory
  despite running in the cluster for 137 days.
- `harness/preflight.py` — detects faults 3, 4 (partially), 6 and 12 statically
  or by live query.
